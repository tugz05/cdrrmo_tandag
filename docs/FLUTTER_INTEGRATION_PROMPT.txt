================================================================================
PROMPT / SPEC FOR FLUTTER DEVELOPER — CDRRMO MOBILE APP (LARAVEL API BACKEND)
================================================================================

Use this document as the product/technical brief when implementing voice-call
flows, operator availability, and related API integration in Flutter.

Base URL: replace with your deployment, e.g. https://your-domain.com
All API examples below use prefix:  {BASE}/api/v1

--------------------------------------------------------------------------------
1) PURPOSE
--------------------------------------------------------------------------------

Before a resident starts a voice call to the operations center, the app must
know whether at least one staff member (admin / super admin) is ONLINE and
AVAILABLE to answer. The backend enforces the same rules when storing the call
location report and on the Twilio voice webhook so users cannot bypass checks.

--------------------------------------------------------------------------------
2) CALL FLOW (RECOMMENDED ORDER)
--------------------------------------------------------------------------------

IMPORTANT — IN-APP CALLING ONLY (TWILIO VOIP):
    Voice connectivity MUST happen entirely inside the Flutter app using the
    Twilio Programmable Voice / Voice SDK (e.g. flutter_twilio_voice or the
    officially supported Twilio mobile SDK path). Do NOT route emergency voice
    through the device’s built-in Phone app: do not use tel: URIs, url_launcher
    to dial, ACTION_DIAL / ACTION_CALL on Android, or any carrier PSTN dialer.
    The third-party integration is Twilio Client-to-Client (or Client-to-server
    TwiML); native dialer bypasses Twilio, loses operator routing, and breaks the
    Laravel/Twilio webhook flow. Users tap “Call” in YOUR UI → SDK connects → audio
    stays in-app.

Step A — Lightweight capacity check (poll sparingly; see section 5).
    GET  /api/v1/call/availability

    If you test mobile voice WITHOUT the web admin dashboard open, you MUST have
    a dispatch client (Flutter or other) logged in as admin and calling:
    POST /api/v1/staff/heartbeat  (Bearer admin Sanctum token, same interval as web ~30s)
    Otherwise `can_connect` stays false (503) and Twilio may later return 31603
    because no `<Dial><Client>` target is registered.

Step B — If can_connect is true, acquire geolocation (if required by UX).

Step C — Store caller location (send Authorization: Bearer <token> so user_id is
    enforced to match the logged-in user):
    POST /api/v1/caller-details/set-location
    Body (JSON): user_id, latitude, longitude, accuracy (optional)

Step D — Obtain Twilio Voice JWT and dial target, then initiate outbound VoIP:
    GET   /api/v1/voice/token
    Headers: Authorization: Bearer <sanctum_token>, Accept: application/json

    Use response fields `token`, `identity`, and `dial_to` with the Twilio Voice
    SDK: register with the JWT, then connect with params To = `dial_to`.

Step E — After the operator answers / call lifecycle (if your app participates):
    POST /api/v1/call/started   { "report_id": <id> }
    POST /api/v1/call/ended     { "report_id": <id> }

Note: /call/started and /call/ended are used by the admin web client today;
confirm with backend whether the mobile app must call these or only the web UI.

CALL SCREEN UI — REALTIME IN-APP SESSION:
    Implement a dedicated call screen (full-screen route or modal) that stays
    visible for the whole Twilio session — do not minimize critical connection
    state to a tiny banner only.

    • Realtime connection states — Bind UI to SDK callbacks so labels update live:
        connecting / ringing / connected / reconnecting / disconnected / failed.
    • Visual polish — Clear typography hierarchy (status headline + subtitle),
      branded colors consistent with CDRRMO, optional subtle pulse or waveform-style
      animation while ringing or connected (avoid clutter; calm “command center”
      feel suits emergency apps).
    • Live duration — Show an elapsed timer from first “connected” until hang-up.
    • Actions — Primary hang-up always visible; mute / speakerphone if the SDK
      supports them; disable controls while reconnecting with explanatory text.
    • Errors — On disconnect or failure, show a clear message and next steps
      (retry availability check, text report option).
    • Accessibility — Screen reader labels for status changes and main buttons.

--------------------------------------------------------------------------------
3) ENDPOINT: CALL AVAILABILITY (FOR FLUTTER)
--------------------------------------------------------------------------------

GET  /api/v1/call/availability
Headers: Accept: application/json
Auth: none (public endpoint)

Rate limit: 120 requests per minute per IP (do not poll every second; see §5).

HTTP status:
  • 200 — at least one operator can take a call right now.
  • 503 — no operator available (all busy or none online).

JSON body (both 200 and 503 include the same keys for parsing convenience):

  can_connect                        bool    — primary flag for UI/logic
  available_operators                int     — count of online + available staff
  total_operators                    int     — count of users with admin roles (configured)
  code                               string  — "OK" or "ALL_OPERATORS_BUSY"
  message                            string  — human-readable message for dialogs/snackbars
  block_reason                       string|null — "NO_ADMIN_ROLE_USERS" | "NO_OPERATOR_ONLINE" | null when OK
  heartbeat_ttl_seconds              int     — heartbeats must arrive within this window (see CALL_STAFF_HEARTBEAT_TTL)
  operator_twilio_client_identity    string  — must match dispatch Twilio Device.register identity (ADMIN_IDENTITY)
  resolution_hint                    string  — non-empty when blocked; explains 503 / 31603 alignment
  twilio_dial_identity               string  — same as operator_twilio_client_identity (use as connect `To`)
  twilio_note                        string  — short reminder for integrators

Example success (200):
  {
    "can_connect": true,
    "available_operators": 1,
    "total_operators": 3,
    "block_reason": null,
    "heartbeat_ttl_seconds": 90,
    "operator_twilio_client_identity": "admin_user",
    "resolution_hint": "",
    "twilio_dial_identity": "admin_user",
    "twilio_note": "Mobile outbound calls TwiML-dial this Client name; dispatch must register Twilio.Device with the same identity.",
    "code": "OK",
    "message": "An operator is available to take your call."
  }

Example unavailable (503):
  {
    "can_connect": false,
    "available_operators": 0,
    "total_operators": 3,
    "block_reason": "NO_OPERATOR_ONLINE",
    "heartbeat_ttl_seconds": 90,
    "operator_twilio_client_identity": "admin_user",
    "resolution_hint": "No operator has a fresh presence heartbeat. Web: keep /admin/dashboard open ... Mobile dispatch: POST /api/v1/staff/heartbeat ...",
    "twilio_dial_identity": "admin_user",
    "twilio_note": "Mobile outbound calls TwiML-dial this Client name; dispatch must register Twilio.Device with the same identity.",
    "code": "ALL_OPERATORS_BUSY",
    "message": "All emergency operators are currently busy. Please try again in a few minutes or use a text report if available."
  }

Flutter UX when 503 or can_connect == false:
  • Show message from `message` or a localized equivalent.
  • Do NOT proceed to Twilio connect or set-location for voice if policy is
    “calls only when operators available.”
  • Optionally offer text-based reporting if the app implements POST /report
    (requires auth:sanctum).

--------------------------------------------------------------------------------
3b) ENDPOINT: STAFF HEARTBEAT (MOBILE DISPATCH / AUTOMATION)
--------------------------------------------------------------------------------

POST  /api/v1/staff/heartbeat
Headers: Authorization: Bearer <sanctum_token_of_admin_or_super_admin>, Accept: application/json
Auth: required (Sanctum)

Success (200): { "status": "ok" }

Call on the same cadence as the web dashboard (~30 seconds). This updates
`staff_presences` so GET /call/availability can return 200 and Twilio voice
webhooks can return connect TwiML instead of busy.

--------------------------------------------------------------------------------
4) ENDPOINT: STORE LOCATION (CALL REPORT)
--------------------------------------------------------------------------------

POST  /api/v1/caller-details/set-location
Headers: Content-Type: application/json, Accept: application/json
Optional: Authorization: Bearer <sanctum_token> — when present, user_id must
match the authenticated user (recommended for Flutter).

Body:
  {
    "user_id": <int>,
    "latitude": <number>,
    "longitude": <number>,
    "accuracy": <number optional>
  }

Success (200):
  {
    "success": true,
    "message": "Caller location stored successfully",
    "report_id": <int>
  }

Failure — all operators busy (503):
  {
    "success": false,
    "code": "ALL_OPERATORS_BUSY",
    "message": "All emergency operators are currently busy. Please try again in a few minutes or use a text report if your app supports it."
  }

Important: The backend rejects creating the report when no operator is available,
so the user does not create orphaned reports when capacity is zero.

--------------------------------------------------------------------------------
5) OPTIMIZATION / BULK TRAFFIC (GUIDANCE FOR FLUTTER)
--------------------------------------------------------------------------------

• Poll GET /call/availability at modest intervals (e.g. every 10–30 seconds while
  on the “call emergency” screen), NOT every frame or every second.
• Back off when receiving HTTP 429 (rate limit) or network errors.
• The server caches availability briefly (~2 seconds default, configurable via
  Laravel env CALL_AVAILABILITY_CACHE_SECONDS) to absorb many simultaneous
  clients checking capacity.

--------------------------------------------------------------------------------
6) TWILIO VOICE TOKEN (MOBILE) & WEBHOOK
--------------------------------------------------------------------------------

Flutter (authenticated resident):
  GET  {BASE}/api/v1/voice/token
  Headers:
    Authorization: Bearer <sanctum_token>
    Accept: application/json

  Response (200):
    {
      "identity": "42",
      "token": "<Twilio access token JWT>",
      "dial_to": "<ADMIN_IDENTITY>",
      "operator_twilio_client_identity": "<same as dial_to>"
    }

  • Use `token` with the Twilio Voice SDK; `identity` is your Twilio client name.
  • Pass `dial_to` (or `operator_twilio_client_identity`) as the `To` parameter when placing the outbound VoIP call to
    the operations center (same value as server env ADMIN_IDENTITY).
  • If the dispatch UI is not registered with that exact Client identity, Twilio returns 31603 / SIP 603 decline.

Admin / test pages (no Sanctum):
  GET  {BASE}/twilio/token?identity=<string>
  (Restrict or remove on production if exposed.)

TwiML webhook (Twilio calls your server):
  POST {BASE}/twilio/voice
  If no operator is available, the server returns TwiML that plays a busy message
  and hangs up — still handle failures gracefully on the client.

--------------------------------------------------------------------------------
7) BACKEND SEMANTICS (FOR CONTEXT ONLY)
--------------------------------------------------------------------------------

• Operators = Laravel users with roles: admin, super_admin (Laratrust).
• “Online” = heartbeat sent within CALL_STAFF_HEARTBEAT_TTL seconds (default 90):
  - Web: POST /admin/staff/heartbeat (session) from AuthenticatedLayout every 30s
  - Mobile dispatch: POST /api/v1/staff/heartbeat (Bearer admin Sanctum token), same effect
• “Busy” = staff answered an incoming call until call finished callback marks
  available again.
• Twilio `<Dial><Client>` uses ADMIN_IDENTITY; the dispatch browser/app must
  `Device.register` with that same string or inbound client dialing fails (31603).
